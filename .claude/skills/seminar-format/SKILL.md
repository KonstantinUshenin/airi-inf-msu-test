# Оформление семинаров

Правила оформления семинаров курса (договорённость от 10 июля). Применяй
**автоматически**, как только создаёшь или редактируешь любой файл в
`seminars/NN-slug/`. Сначала пиши по этим правилам, в конце — пройди
чек-лист самопроверки.

Термины — в корневом `CONTEXT.md`. Пример эталонного оформления задач —
`seminars/02-unix-files/tasks.md` и `seminars/02-unix-files/solutions.md`.

## Структура семинара

Каждый семинар — каталог `seminars/NN-slug/`:

- `NN` — двузначный номер семинара с ведущим нулём, совпадает со строкой в
  таблице плана (`seminars/README.md`). Ведущий ноль нужен, чтобы `10` не
  сортировался перед `2`.
- `slug` — короткое английское имя темы через дефис (`unix-files`, `unix-ssh`),
  чтобы каталог был самоописывающим. Пробелов в имени быть не должно.

Внутри — три обязательных файла и, при необходимости, каталог с данными:

| Файл | Что содержит |
|------|--------------|
| `demo.ipynb` | Микро-лекция: мотивация + короткая демка + вопросы для коммуникации |
| `tasks.md` | Формулировки задач по уровням (база / среднее / сложное) |
| `solutions.md` | Примеры решений, по одному на каждую задачу |
| `images/*.svg` | Схемы к микро-лекции (если тема их требует, см. п. 1.9) |
| `assets/` | Необязательный: данные и файлы, нужные задачам |

Микро-лекция лежит в `demo.ipynb`, а не в `lecture.ipynb`: настоящие лекции
курса живут в `lectures/` и нумеруются отдельно, поэтому имя `lecture` внутри
семинара путало бы студентов.

Задачи решаются в консоли или Jupyter. Не смешивай формулировки и решения в
одном файле.

## 1. Микро-лекция (`demo.ipynb`)

Короткая (10–15 минут) крутая демка / напоминание темы с лекции. Правила:

1. **Мотивация — обязательно в самом начале.** Первая markdown-ячейка
   объясняет студентам, *почему и зачем* это нужно: где пригодится, какую
   боль решает. Без мотивации микро-лекция не принимается.
2. **Короткие простые примеры — не больше 8 строк кода в ячейке.** Демо-ячейки
   (`%%bash`, Python и т.п.) маленькие и самодостаточные: одна идея на ячейку.
   Считаются содержательные строки: пустые, комментарии и строка `%%bash` не в
   счёт. Не влезает в 8 строк — значит, это не одна идея; разбейте на две
   ячейки с пояснением между ними.

   **Одна новая концепция за ячейку.** Материал усложняется постепенно: если
   ячейка вводит сразу и новую библиотеку, и новый приём, и новый формат данных
   — разнесите. Машина это не проверяет, следит автор и ревьюер.

3. **Одна ячейка — один шаг сюжета.** Восемь строк — это потолок, а не цель.
   Если ячейка сначала готовит обстановку, а потом на ней что-то показывает —
   это два шага, и они должны быть в разных ячейках с markdown-пояснением
   между ними. Признак, что пора делить: внутри ячейки мысленно просится
   «а теперь…» или в коде появилась пустая строка-разделитель.

   Плохо — одна ячейка и сорит в репозитории, и разбирает, что получилось:

   ```bash
   %%bash
   cd ~/seminar-04/git-demo || exit 1
   touch checkpoint.pt nohup.out
   mkdir -p __pycache__ && touch __pycache__/x.pyc

   git status --short            # ?? = git про эти файлы ничего не знает
   git clean -nd                 # только показать, что будет удалено
   ```

   Хорошо: первая ячейка засоряет репозиторий и показывает `git status`,
   markdown между ними объясняет, что означает `??`, вторая ячейка убирает
   мусор через `git clean`. Тогда у каждой ячейки один результат, который можно
   обсудить с аудиторией, и любую из них можно перезапустить отдельно.

4. **Комментарии в коде обязательны.** Студент возвращается к ноутбуку без
   преподавателя рядом, поэтому из самой ячейки должно быть видно, что делает
   строка и что она покажет. Комментируй **в коде**, а не только в markdown
   вокруг:

   - у каждой неочевидной содержательной строки — комментарий в конце строки
     (`git clean -nd    # только показать, что будет удалено`);
   - при необходимости строка-комментарий сверху — что мы сейчас делаем;
   - комментарий объясняет **зачем и что получится**, а не пересказывает
     синтаксис: `# создаём файл` к `touch x` — мусор, `# ?? = git про этот файл
     ничего не знает` — польза.

   Комментарии не съедают лимит в 8 строк — они не считаются содержательными
   строками, так что выбор между «покороче» и «понятнее» делать не нужно.
   Markdown-ячейка вокруг никуда не девается: она про идею, комментарий — про
   конкретную строку. Ячейка совсем без комментариев допустима, только если это
   одна-две очевидные строки.

5. **Вопросы для коммуникации по ходу.** Чтобы выстроить диалог с
   аудиторией, вставляй вопросы в markdown-ячейки. Формат — строго такой
   (свёрнутый ответ в `<details>`):

```markdown
#### ❓ **Вопрос**: Текст вопроса?

<details>

<summary><strong>Ответ</strong></summary>

Текст ответа

</details>
```

Минимум несколько таких вопросов на микро-лекцию; ответ на каждый должен
следовать из показанной демки.

6. **Интересные факты и детали — в заметку преподавателя.** Ноутбук не должен
   быть конспектом: если деталь или байка нужна для живого рассказа, а не для
   работы за терминалом, она прячется в свёрнутый блок. Так у ведущего остаётся,
   что рассказать, а студент разворачивает блок при подготовке к защите. Формат:

```markdown
<details>

<summary>🎙 <em>Заметка преподавателя — рассказывается вслух</em></summary>

Текст заметки

</details>
```

   Признак того, что абзац пора отправить в заметку: он не нужен, чтобы
   выполнить следующую ячейку, и не отвечает ни на один вопрос из
   теор-минимума. Историю технологии, оговорки про документацию, «а вот у нас
   на проекте» — туда.

7. **Работаем в домашнем каталоге студента, а не в `/tmp`.** Демонстрация и
   задачи выполняются на виртуальной машине студента, в каталоге вида
   `~/seminar-NN/`: `/tmp` вычищается при перезагрузке, а результат нужен и
   после занятия. Если ячейка делает `rm -rf` для чистого старта, путь пишется
   целиком и без переменных, а `cd` в рабочий каталог — с `|| exit 1`.

8. **Один оператор — одна строка.** В Python-ячейках не объединяй несколько
   операторов через `;` в одной строке (например,
   `plt.xlabel("x"); plt.ylabel("y")` или `plt.legend(); plt.grid(True)`) — это
   ухудшает читаемость и диффы. Пиши каждый вызов на отдельной строке. (Правило
   про Python; `;` в тексте Markdown и в shell-однострочниках `python -c "..."`
   не считается.)

9. **Визуализации — планируй их до того, как писать текст.** Прежде чем
   набирать микро-лекцию, пройдись по её плану и выпиши, какие места просят
   схему. Картинка обязана нести смысл, которого нет в тексте и в выводе
   терминала; декоративных иллюстраций не делаем.

   **Что рисовать:**
   - **пространственное** — что где лежит и как связано (зоны, копии
     репозитория, слои системы);
   - **временное** — как состояние меняется по шагам (2–4 кадра подряд);
   - **то, что путают** — две похожие вещи рядом, различие подсвечено;
   - **выигрыш алгоритма** — было N шагов, стало log N.

   **Что не рисовать:** синтаксис и списки правил (это текст), содержимое
   вывода команды (это демо-ячейка), «общую картину мира» без конкретики.

   **Формат.** Только SVG, отдельными файлами в `seminars/NN-slug/images/`,
   имена вида `01-краткое-имя.svg`. В markdown-ячейку рядом с объясняемым
   местом картинка вставляется **как data-URI**
   (`![Подпись](data:image/svg+xml;base64,…)`), а не относительной ссылкой:
   относительные пути внутри `.ipynb` GitHub не резолвит, и студент увидит
   битую иллюстрацию. Файл в `images/` остаётся источником правды, ноутбук
   собирается из него скриптом. Требования к файлу:
   - самодостаточный: без внешних шрифтов, скриптов и ссылок на сеть;
   - непрозрачная светлая подложка `<rect>` на весь холст — иначе тёмная тема
     превратит чёрный текст в невидимый;
   - `font-family` — системный стек (`system-ui, Arial, sans-serif`), кириллица
     обязана читаться;
   - у маркеров-стрелок `orient="auto"`, **не** `auto-start-reverse`: часть
     рендереров его не понимает и разворачивает наконечники;
   - подпись-вывод внизу картинки одной строкой: что именно читатель должен
     отсюда унести.

   **Проверка перед сдачей:** отрендерить каждый файл в растр и посмотреть
   глазами. Типовые дефекты, которые видны только на рендере: текст выехал за
   границу холста, подписи наложились друг на друга, стрелка смотрит не туда.

## 2. Задачи (`tasks.md`)

- **Три уровня**: `## База`, `## Среднее`, `## Сложное`.
- **5–10 задач НА КАЖДЫЙ уровень** — с запасом, чтобы разные преподаватели
  могли выбирать (это банк задач, а не то, что решает один студент). См.
  `docs/adr/0002-tasks-per-level-not-per-seminar.md`.
- **Нумеровать по уровню** во избежание путаницы: база — `B1, B2, …`,
  среднее — `M1, M2, …`, сложное — `H1, H2, …`.
- **Тестовый пример по возможности у каждой задачи.** Если просят написать
  скрипт — привести пример входных аргументов и что он вернёт; если задача не
  про скрипт — привести вход → ожидаемый результат (или аналог проверки).
- **`**need:**`** — строка сразу после заголовка задачи, описывающая
  необходимую подготовку/предусловия (или `нет`).
- **База — отслеживаемый минимум.** Базовые задачи вынесены в раздел
  `## База`; именно по ним отмечают, кто их решил.

Шаблон задачи:

```markdown
### B1. Короткое имя

**need:** предусловия или `нет`.

Формулировка задачи одним-двумя абзацами.

**Пример:** `script.sh input.txt` → выводит `3` (число строк).
```

## 3. Ответы (`solutions.md`)

- Один блок решения на каждую задачу, под тем же идентификатором (`### B1`,
  `### M1`, `### H1`).
- Решение — минимальный рабочий пример (код в ```` ```bash ````/```` ```python ````),
  дающий результат из тестового примера.
- Порядок и нумерация решений совпадают с `tasks.md`.
- **Один оператор — одна строка**: в Python не объединяй вызовы через `;`
  (`plt.legend(); plt.grid(True)`) — каждый на своей строке.

## 4. Защита и оценивание

Правила защиты (учитывай при подготовке материалов — теор-минимум должен быть
выводим из микро-лекции и задач):

- Все студенты защищают сделанные задания семинаристам.
- Нет ответа на вопрос из **теор-минимума** (без которого нельзя было получить
  результат) → **0 баллов** за работу.
- Нет ответа на **дополнительный** вопрос → балл может быть снижен.

## Чек-лист самопроверки (перед завершением правки семинара)

Пройди по пунктам для затронутых файлов:

**`demo.ipynb`**
- [ ] Первая ячейка — блок мотивации (почему и зачем).
- [ ] Короткие самодостаточные демо-ячейки.
- [ ] Каждая ячейка — один шаг: подготовка обстановки и разбор результата разнесены.
- [ ] В коде есть комментарии: что делает неочевидная строка и что получится.
- [ ] Есть вопросы для коммуникации в точном формате `#### ❓ **Вопрос**` + `<details>`.
- [ ] На каждый вопрос ответ следует из показанной демки.
- [ ] Факты и детали «для устного рассказа» убраны в блоки `🎙 Заметка
      преподавателя`, а не лежат основным текстом.
- [ ] Пути в ячейках — в домашнем каталоге (`~/seminar-NN/…`), `/tmp` не
      используется; у `cd` есть `|| exit 1`.
- [ ] В Python-ячейках нет нескольких операторов через `;` в одной строке.
- [ ] План визуализаций продуман: для каждого пространственного/пошагового
      места либо есть схема, либо явно решено, что она не нужна.
- [ ] Схемы лежат в `images/` как SVG, вставлены рядом с объясняемым местом,
      каждая отрендерена и просмотрена глазами (текст не выехал, стрелки на
      месте).

**`tasks.md`**
- [ ] Присутствуют все три уровня: База / Среднее / Сложное.
- [ ] 5–10 задач на каждом уровне.
- [ ] Нумерация по уровню (`B*` / `M*` / `H*`).
- [ ] У каждой задачи есть `**need:**` и, по возможности, тестовый пример.
- [ ] В преамбуле сказано, что работаем в домашнем каталоге, а не в `/tmp`.

**`solutions.md`**
- [ ] Ровно по одному решению на каждую задачу из `tasks.md`, те же идентификаторы.
- [ ] Решение воспроизводит результат из тестового примера.
- [ ] В Python-решениях нет нескольких операторов через `;` в одной строке.

Если какой-то пункт не выполнить осмысленно — явно скажи об этом в ответе, а не
молча пропусти.

## Линтер

Механическую часть правил проверяет `tools/lint_seminars.py` — прогони его
перед тем, как считать правку законченной:

```bash
python3 tools/lint_seminars.py                  # все семинары
python3 tools/lint_seminars.py seminars/04-git  # один
python3 tools/lint_seminars.py --stats          # + длины всех кодовых ячеек
python3 tools/lint_seminars.py --changed main   # только затронутые вашей веткой
```

Автоматика гоняет как раз `--changed`: и в pull request, и на push проверяются
только семинары, которых коснулось изменение. Чужой долг разгребать не придётся,
но свой семинар обязан проходить линтер начисто.

Он ловит только формальное: больше 8 строк кода в ячейке, старый формат
вопросов, отсутствие мотивации, несколько операторов через `;` в строке, схему
имён каталогов, число задач по уровням и их идентификаторы, строку `**need:**`,
расхождение `tasks.md` и `solutions.md`. Всё смысловое (мотивация действительно
объясняет «зачем», ответ выводим из демки, одна ли новая концепция и один ли
шаг в ячейке, объясняют ли комментарии в коде происходящее, не используются ли
инструменты, исключённые из курса, картинка несёт смысл) проверяет человек на
ревью.

Исключений у линтера нет: правило либо соблюдается, либо проверка красная.
Список «известного долга» не ведём — если старое правило где-то нарушено, это
надо чинить, а не записывать в разрешённые.
