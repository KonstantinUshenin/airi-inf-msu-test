# Оформление семинаров

Правила оформления семинаров курса (договорённость от 10 июля). Применяй
**автоматически**, как только создаёшь или редактируешь любой файл в
`seminars/seminar N/`. Сначала пиши по этим правилам, в конце — пройди
чек-лист самопроверки.

Термины — в корневом `CONTEXT.md`. Пример эталонного оформления задач —
`seminars/seminar 2/question.md` и `seminars/seminar 2/answer.md`.

## Структура семинара (3 файла)

Каждый семинар — каталог `seminars/seminar N/` c тремя файлами:

| Файл | Что содержит |
|------|--------------|
| `lecture.ipynb` | Микро-лекция: мотивация + короткая демка + вопросы для коммуникации |
| `question.md` | Формулировки задач по уровням (база / среднее / сложное) |
| `answer.md` | Примеры решений, по одному на каждую задачу |
| `images/*.svg` | Схемы к микро-лекции (если тема их требует, см. п. 1.5) |

Задачи решаются в консоли или Jupyter. Не смешивай формулировки и решения в
одном файле.

## 1. Микро-лекция (`lecture.ipynb`)

Короткая (10–15 минут) крутая демка / напоминание темы с лекции. Правила:

1. **Мотивация — обязательно в самом начале.** Первая markdown-ячейка
   объясняет студентам, *почему и зачем* это нужно: где пригодится, какую
   боль решает. Без мотивации микро-лекция не принимается.
2. **Короткие простые примеры.** Демо-ячейки (`%%bash`, Python и т.п.)
   маленькие и самодостаточные — одна идея на ячейку.
3. **Вопросы для коммуникации по ходу.** Чтобы выстроить диалог с
   аудиторией, вставляй вопросы в markdown-ячейки. Формат — строго такой
   (свёрнутый ответ в `<details>`):

```markdown
#### ❓ **Вопрос**: Текст вопроса?

<details>

<summary><strong>Ответ</strong></summary>

Текст ответа

</details>
```

Минимум несколько таких вопросов на микро-лекцию; ответ на каждый должен
следовать из показанной демки.

4. **Один оператор — одна строка.** В Python-ячейках не объединяй несколько
   операторов через `;` в одной строке (например,
   `plt.xlabel("x"); plt.ylabel("y")` или `plt.legend(); plt.grid(True)`) — это
   ухудшает читаемость и диффы. Пиши каждый вызов на отдельной строке. (Правило
   про Python; `;` в тексте Markdown и в shell-однострочниках `python -c "..."`
   не считается.)

5. **Визуализации — планируй их до того, как писать текст.** Прежде чем
   набирать микро-лекцию, пройдись по её плану и выпиши, какие места просят
   схему. Картинка обязана нести смысл, которого нет в тексте и в выводе
   терминала; декоративных иллюстраций не делаем.

   **Что рисовать:**
   - **пространственное** — что где лежит и как связано (зоны, копии
     репозитория, слои системы);
   - **временное** — как состояние меняется по шагам (2–4 кадра подряд);
   - **то, что путают** — две похожие вещи рядом, различие подсвечено;
   - **выигрыш алгоритма** — было N шагов, стало log N.

   **Что не рисовать:** синтаксис и списки правил (это текст), содержимое
   вывода команды (это демо-ячейка), «общую картину мира» без конкретики.

   **Формат.** Только SVG, отдельными файлами в `seminars/seminar N/images/`,
   имена вида `01-краткое-имя.svg`. В markdown-ячейку рядом с объясняемым
   местом картинка вставляется **как data-URI**
   (`![Подпись](data:image/svg+xml;base64,…)`), а не относительной ссылкой:
   относительные пути внутри `.ipynb` GitHub не резолвит, и студент увидит
   битую иллюстрацию. Файл в `images/` остаётся источником правды, ноутбук
   собирается из него скриптом. Требования к файлу:
   - самодостаточный: без внешних шрифтов, скриптов и ссылок на сеть;
   - непрозрачная светлая подложка `<rect>` на весь холст — иначе тёмная тема
     превратит чёрный текст в невидимый;
   - `font-family` — системный стек (`system-ui, Arial, sans-serif`), кириллица
     обязана читаться;
   - у маркеров-стрелок `orient="auto"`, **не** `auto-start-reverse`: часть
     рендереров его не понимает и разворачивает наконечники;
   - подпись-вывод внизу картинки одной строкой: что именно читатель должен
     отсюда унести.

   **Проверка перед сдачей:** отрендерить каждый файл в растр и посмотреть
   глазами. Типовые дефекты, которые видны только на рендере: текст выехал за
   границу холста, подписи наложились друг на друга, стрелка смотрит не туда.

## 2. Задачи (`question.md`)

- **Три уровня**: `## База`, `## Среднее`, `## Сложное`.
- **5–10 задач НА КАЖДЫЙ уровень** — с запасом, чтобы разные преподаватели
  могли выбирать (это банк задач, а не то, что решает один студент). См.
  `docs/adr/0002-tasks-per-level-not-per-seminar.md`.
- **Нумеровать по уровню** во избежание путаницы: база — `B1, B2, …`,
  среднее — `M1, M2, …`, сложное — `H1, H2, …`.
- **Тестовый пример по возможности у каждой задачи.** Если просят написать
  скрипт — привести пример входных аргументов и что он вернёт; если задача не
  про скрипт — привести вход → ожидаемый результат (или аналог проверки).
- **`**need:**`** — строка сразу после заголовка задачи, описывающая
  необходимую подготовку/предусловия (или `нет`).
- **База — отслеживаемый минимум.** Базовые задачи вынесены в раздел
  `## База`; именно по ним отмечают, кто их решил.

Шаблон задачи:

```markdown
### B1. Короткое имя

**need:** предусловия или `нет`.

Формулировка задачи одним-двумя абзацами.

**Пример:** `script.sh input.txt` → выводит `3` (число строк).
```

## 3. Ответы (`answer.md`)

- Один блок решения на каждую задачу, под тем же идентификатором (`### B1`,
  `### M1`, `### H1`).
- Решение — минимальный рабочий пример (код в ```` ```bash ````/```` ```python ````),
  дающий результат из тестового примера.
- Порядок и нумерация решений совпадают с `question.md`.
- **Один оператор — одна строка**: в Python не объединяй вызовы через `;`
  (`plt.legend(); plt.grid(True)`) — каждый на своей строке.

## 4. Защита и оценивание

Правила защиты (учитывай при подготовке материалов — теор-минимум должен быть
выводим из микро-лекции и задач):

- Все студенты защищают сделанные задания семинаристам.
- Нет ответа на вопрос из **теор-минимума** (без которого нельзя было получить
  результат) → **0 баллов** за работу.
- Нет ответа на **дополнительный** вопрос → балл может быть снижен.

## Чек-лист самопроверки (перед завершением правки семинара)

Пройди по пунктам для затронутых файлов:

**`lecture.ipynb`**
- [ ] Первая ячейка — блок мотивации (почему и зачем).
- [ ] Короткие самодостаточные демо-ячейки.
- [ ] Есть вопросы для коммуникации в точном формате `#### ❓ **Вопрос**` + `<details>`.
- [ ] На каждый вопрос ответ следует из показанной демки.
- [ ] В Python-ячейках нет нескольких операторов через `;` в одной строке.
- [ ] План визуализаций продуман: для каждого пространственного/пошагового
      места либо есть схема, либо явно решено, что она не нужна.
- [ ] Схемы лежат в `images/` как SVG, вставлены рядом с объясняемым местом,
      каждая отрендерена и просмотрена глазами (текст не выехал, стрелки на
      месте).

**`question.md`**
- [ ] Присутствуют все три уровня: База / Среднее / Сложное.
- [ ] 5–10 задач на каждом уровне.
- [ ] Нумерация по уровню (`B*` / `M*` / `H*`).
- [ ] У каждой задачи есть `**need:**` и, по возможности, тестовый пример.

**`answer.md`**
- [ ] Ровно по одному решению на каждую задачу из `question.md`, те же идентификаторы.
- [ ] Решение воспроизводит результат из тестового примера.
- [ ] В Python-решениях нет нескольких операторов через `;` в одной строке.

Если какой-то пункт не выполнить осмысленно — явно скажи об этом в ответе, а не
молча пропусти.
