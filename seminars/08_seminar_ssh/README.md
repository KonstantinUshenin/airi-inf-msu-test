# Семинар 8. Unix-terminal. SSH

## Цель

Научиться настраивать и использовать SSH для удалённого доступа, безопасно управлять ключами, передавать файлы и синхронизировать каталоги между машинами, а также строить SSH-туннели для проброса портов. Результаты фиксировать в отчёте, артефакты (конфиги, скрипты, выводы команд) сохранять на диске.

## Теоретический минимум

- **SSH (Secure Shell):** протокол для зашифрованного удалённого доступа; порт 22/tcp по умолчанию; клиент (`ssh`) и сервер (`sshd`).
- **Аутентификация:** два основных способа — по паролю и по ключу (предпочтительнее); принцип работы challenge-response с открытым/закрытым ключом.
- **ssh-keygen:** генерация пар ключей (RSA, Ed25519); файлы `~/.ssh/id_ed25519` (закрытый) и `~/.ssh/id_ed25519.pub` (открытый); парольная фраза (passphrase) для защиты закрытого ключа.
- **authorized_keys:** файл `~/.ssh/authorized_keys` на сервере — список открытых ключей, которым разрешён вход; права доступа (`chmod 600`).
- **SSH-конфиг:** файл `~/.ssh/config` — алиасы хостов, пользователь, порт, путь к ключу, ProxyJump; упрощает повседневную работу.
- **scp:** копирование файлов по SSH; синтаксис `scp local user@host:remote` и обратно; рекурсивное копирование (`-r`).
- **rsync:** инкрементальная синхронизация; ключевые флаги (`-avz`, `--delete`, `--exclude`); преимущества над `scp` (передаёт только изменения, сжатие, возобновление).
- **SSH-туннели:** локальный проброс (`-L`), удалённый проброс (`-R`), динамический SOCKS-прокси (`-D`); типичные сценарии (доступ к БД за NAT, обход блокировки порта).
- **ssh-agent:** кеширование расшифрованных ключей в памяти; `ssh-add` для добавления ключей; `SSH_AUTH_SOCK`.

## Задачи

1. **Генерация SSH-ключей**
   - Сгенерировать пару ключей Ed25519: `ssh-keygen -t ed25519 -C "student@seminar8"`.
   - При генерации задать парольную фразу (passphrase).
   - Вывести содержимое открытого ключа (`cat ~/.ssh/id_ed25519.pub`); записать в отчёт формат ключа (алгоритм, ключ, комментарий).
   - Проверить права на файлы: `ls -la ~/.ssh/`; убедиться, что закрытый ключ имеет права `600`, каталог `~/.ssh` — `700`.
   - Объяснить в отчёте: почему закрытый ключ нельзя передавать и зачем нужна парольная фраза.

2. **Настройка доступа по ключу**
   - Скопировать открытый ключ на удалённый сервер: `ssh-copy-id user@server` (или вручную: `cat ~/.ssh/id_ed25519.pub | ssh user@server 'cat >> ~/.ssh/authorized_keys'`).
   - Подключиться к серверу по SSH без ввода пароля; зафиксировать успех в отчёте.
   - На сервере проверить содержимое `~/.ssh/authorized_keys` — убедиться, что ключ добавлен.
   - Если удалённый сервер недоступен: настроить доступ к localhost (запустить `sshd` локально или использовать `ssh localhost`).

3. **SSH-конфиг**
   - Создать или дополнить файл `~/.ssh/config` записью для учебного сервера:
     ```
     Host seminar
         HostName <IP или домен>
         User <username>
         IdentityFile ~/.ssh/id_ed25519
         Port 22
     ```
   - Подключиться с использованием алиаса: `ssh seminar`; зафиксировать результат.
   - Добавить в конфиг параметр `ServerAliveInterval 60` — объяснить в отчёте, зачем он нужен.
   - Добавить запись с `ProxyJump` для доступа через промежуточный хост (jump host):
     ```
     Host internal
         HostName 10.0.0.5
         User student
         ProxyJump seminar
     ```
     Объяснить в отчёте сценарий использования ProxyJump (доступ к машине за NAT).

4. **Копирование файлов (scp)**
   - Скопировать файл с локальной машины на сервер: `scp localfile.txt user@server:/tmp/`.
   - Скопировать файл с сервера на локальную машину: `scp user@server:/etc/hostname ./hostname_remote.txt`.
   - Скопировать каталог рекурсивно: `scp -r ./mydir user@server:/tmp/mydir_copy`.
   - Проверить, что файлы скопировались (`ls`, `md5sum`/`sha256sum`); зафиксировать результат.

5. **Синхронизация каталогов (rsync)**
   - Создать локальный каталог с несколькими файлами (текст, скрипт, картинка).
   - Синхронизировать каталог на сервер: `rsync -avz ./mydir/ user@server:/tmp/mydir_sync/`.
   - Изменить один файл локально и выполнить `rsync` повторно; обратить внимание на вывод — убедиться, что передаётся только изменённый файл.
   - Использовать `--dry-run` для предварительного просмотра действий без фактической передачи.
   - Добавить `--exclude '*.log'` — убедиться, что `.log`-файлы не копируются.
   - Описать в отчёте преимущества `rsync` перед `scp` (инкрементальность, сжатие, `--delete`).

6. **SSH-туннели: локальный проброс (-L)**
   - На удалённом сервере запустить простой HTTP-сервер: `python3 -m http.server 8080 --bind 127.0.0.1` (доступен только локально на сервере).
   - С локальной машины создать туннель: `ssh -L 9090:127.0.0.1:8080 user@server -N`.
   - Открыть в браузере или через `curl http://localhost:9090` — убедиться, что виден контент удалённого сервера.
   - Зафиксировать в отчёте: команду, схему соединения, результат.

7. **SSH-туннели: удалённый проброс (-R)**
   - На локальной машине запустить сервис на порту 3000 (например, `python3 -m http.server 3000`).
   - Создать обратный туннель: `ssh -R 8888:127.0.0.1:3000 user@server -N`.
   - На сервере выполнить `curl http://localhost:8888` — убедиться, что виден контент с локальной машины.
   - Описать в отчёте сценарий: зачем нужен удалённый проброс (например, демонстрация локального приложения коллегам без публичного IP).

8. **ssh-agent и управление ключами**
   - Запустить агент: `eval $(ssh-agent)`.
   - Добавить ключ: `ssh-add ~/.ssh/id_ed25519` (ввести парольную фразу один раз).
   - Проверить загруженные ключи: `ssh-add -l`.
   - Подключиться к серверу — убедиться, что парольная фраза не запрашивается повторно.
   - Удалить ключ из агента: `ssh-add -d ~/.ssh/id_ed25519`; попробовать подключиться снова.
   - Описать в отчёте: как `ssh-agent` упрощает работу и как он связан с переменной `SSH_AUTH_SOCK`.

9. **Комплексное задание: скрипт для деплоя**
   - Написать bash-скрипт `deploy.sh`, который:
     - принимает аргумент — путь к локальному каталогу с проектом;
     - синхронизирует каталог на удалённый сервер с помощью `rsync` (с исключением `.git/`, `__pycache__/`, `*.pyc`);
     - подключается по SSH и перезапускает сервис (например, `ssh seminar 'systemctl --user restart myapp'` или аналог);
     - выводит статус сервиса после перезапуска.
   - Запустить скрипт, зафиксировать вывод в отчёте.
   - Если удалённый сервер недоступен: выполнить `rsync` на localhost и вместо перезапуска сервиса — вывести сообщение и содержимое синхронизированного каталога.

10. **Логи sshd и брутфорс-атаки**
   - Просмотреть логи SSH-сервера: `sudo journalctl -u sshd --no-pager -n 200` (systemd) или `sudo cat /var/log/auth.log | grep sshd` (Debian/Ubuntu) / `sudo cat /var/log/secure | grep sshd` (CentOS/RHEL).
   - Найти записи о неудачных попытках входа: `sudo journalctl -u sshd | grep -i 'failed\|invalid'`; обратить внимание на IP-адреса, имена пользователей (root, admin, test и т.п.) и частоту попыток.
   - С помощью `grep` и `sort | uniq -c | sort -rn` вывести топ-10 IP-адресов по числу неудачных попыток входа; выполнить `whois` для нескольких из них — определить страну и провайдера.
   - Ответить в отчёте: какие имена пользователей чаще всего перебирают, с каких подсетей идут атаки, почему важно отключать вход по паролю и запрещать root-логин.

11. **Защита от перебора: fail2ban**
   - Установить `fail2ban`: `sudo apt install fail2ban` (или аналог для вашего дистрибутива).
   - Просмотреть конфигурацию по умолчанию: `cat /etc/fail2ban/jail.conf | grep -A 10 '\[sshd\]'`.
   - Создать локальный override: скопировать `sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local` и в `jail.local` настроить секцию `[sshd]`:
     ```
     [sshd]
     enabled = true
     port = ssh
     maxretry = 5
     findtime = 600
     bantime = 3600
     ```
   - Запустить сервис: `sudo systemctl enable --now fail2ban`.
   - Проверить статус jail для SSH: `sudo fail2ban-client status sshd` — зафиксировать количество забаненных IP.
   - Просмотреть лог `fail2ban`: `sudo tail -50 /var/log/fail2ban.log`; найти записи о банах.
   - Объяснить в отчёте: что означают параметры `maxretry`, `findtime`, `bantime`; как `fail2ban` взаимодействует с `iptables`/`nftables`; как разбанить IP вручную (`sudo fail2ban-client set sshd unbanip <IP>`).

Отчёт и артефакты (конфиги, скрипты, выводы команд) хранить в репозитории семинара или в Jupyter-ноутбуке / на удалённом сервере по указанию преподавателя.

## Бонусные задачи

- **Динамический SOCKS-прокси:** создать SSH-туннель с `-D 1080`; настроить браузер (или `curl --socks5`) для использования SOCKS-прокси через `localhost:1080`; открыть `https://ifconfig.me` и убедиться, что IP-адрес соответствует серверу, а не локальной машине; описать в отчёте, чем SOCKS-прокси отличается от локального проброса порта.
- **Hardening SSH-сервера:** на учебном сервере (или в виртуальной машине) внести изменения в `/etc/ssh/sshd_config`: отключить аутентификацию по паролю (`PasswordAuthentication no`), запретить вход root (`PermitRootLogin no`), сменить порт на нестандартный; перезапустить `sshd` и проверить, что подключение работает только по ключу; описать каждое изменение и его назначение в отчёте.
- **Multiplexing и ControlMaster:** добавить в `~/.ssh/config` параметры `ControlMaster auto`, `ControlPath ~/.ssh/sockets/%r@%h-%p`, `ControlPersist 600`; выполнить несколько подключений к одному серверу и измерить время установки соединения (первое vs последующие с помощью `time ssh seminar exit`); объяснить в отчёте принцип мультиплексирования SSH-соединений.
