# Практическая работа

**Выход:** `.sh` или `.ipynb` с командами и их выводом.

Все задачи выполняются **на своей виртуальной машине, в домашнем каталоге** —
например, в `~/seminar-08/`. Каталог `/tmp` не используем: он вычищается при
перезагрузке, а ключи, конфиги и логи нужны вам до защиты.

Где в формулировках написано `course` — это ваш учебный сервер: либо полная
запись `user@host`, либо короткое имя из `~/.ssh/config`. Учебные ключи держите
в `~/seminar-08/keys/`, а не в `~/.ssh/`, чтобы не перемешать их с рабочими.

Задачи разбиты на три уровня. Базовые задачи — обязательный минимум, по ним
отмечают, кто их решил. Список с запасом: преподаватель выбирает, что давать.

## База — 7 задач

### B1. SSH-клиент

**need:** SSH-клиент.

Создайте отчёт с версией SSH, путём к клиенту и итоговой конфигурацией тестового хоста.

**Пример:** `cat ~/seminar-08/logs/ssh-client.txt` → первая строка вида
`OpenSSH_9.6p1 ...`, дальше `/usr/bin/ssh` и строки `hostname`/`user`/`port` из `ssh -G`.

### B2. Удалённая система

**need:** учебный SSH-сервер.

Сохраните имя удалённого хоста, пользователя, текущий каталог, kernel и операционную систему.

**Пример:** в файле-отчёте первые строки — имя сервера и ваш логин на нём,
а не имя вашей виртуалки.

### B3. Удалённые потоки

**need:** учебный SSH-сервер.

Получите от удалённой команды stdout, stderr и код завершения. Сохраните потоки раздельно.

**Пример:** `ssh course 'ls /etc/os-release /missing-file'` → в stdout строка
`/etc/os-release`, в stderr `No such file or directory`, код завершения `2`.

### B4. Передача файла

**need:** учебный SSH-сервер; локальный текстовый файл.

Передайте файл на сервер, получите его обратно под другим именем. Подтвердите совпадение размеров и содержимого.

**Пример:** `wc -c` для обоих файлов даёт одинаковое число, а `cmp` завершается
с кодом `0` и ничего не печатает.

### B5. SSH-конфигурация

**need:** данные учебного SSH-сервера.

Создайте отдельный SSH-config с псевдонимом `course`. Сохраните итоговые host, user и port.

**Пример:** `ssh -T -F ~/seminar-08/ssh/course-config -G course` → строки
`hostname ВАШ_СЕРВЕР`, `user ВАШ_ЛОГИН`, `port 22`.

### B6. Кавычки в удалённой команде

**need:** учебный SSH-сервер.

Выполните одну и ту же команду `echo $HOME` на сервере дважды: в двойных и в
одинарных кавычках. Сохраните оба вывода и объясните в комментарии, почему они
разные.

**Пример:** `ssh course "echo $HOME"` → `/home/student-laptop` (ваш локальный
путь), `ssh course 'echo $HOME'` → `/home/student` (путь на сервере).

### B7. Ключи в `ssh-agent`

**need:** пара ключей из `~/seminar-08/keys/`.

Поднимите `ssh-agent` в текущей оболочке, добавьте в него закрытый ключ,
сохраните список отпечатков, которые агент готов предъявлять, и погасите агент.

**Пример:** `ssh-add -l` → строка вида
`256 SHA256:jD9wJS4... course-key (ED25519)`; после `ssh-agent -k` та же
команда сообщает, что подключиться к агенту не может.

## Среднее — 7 задач

### M1. SSH-ключ

**need:** каталог для учебного ключа.

Создайте ключ ed25519, установите закрытому ключу права `400` и сохраните fingerprint публичного ключа. Закрытый ключ не выводите.

**Пример:** `ls -l ~/seminar-08/keys` → у закрытого ключа права `-r--------`;
`ssh-keygen -lf ...pub` → `256 SHA256:... course-key (ED25519)`.

### M2. Сессия tmux

**need:** учебный SSH-сервер с `tmux`.

Создайте на сервере detached-сессию `course-worker` с процессом длительностью 120 секунд. Отключитесь, подключитесь снова, сохраните список сессий и состояние процесса. Завершите сессию и подтвердите её отсутствие.

**Пример:** `tmux list-sessions` → `course-worker: 1 windows (created ...)`;
после `kill-session` — `has-session` возвращает ненулевой код.

### M3. Синхронизация

**need:** учебный SSH-сервер; `rsync`; локальный каталог с файлами.

Синхронизируйте содержимое локального каталога с удалённым. Повторный запуск не должен передавать неизменённые файлы.

**Пример:** в первом прогоне список файлов непустой, во втором после
`sending incremental file list` файлов нет, а `speedup` заметно вырастает.

### M4. Known hosts

**need:** учебный SSH-сервер; отдельный файл known_hosts.

Добавьте запись учебного сервера в отдельный known_hosts. Найдите её по имени хоста и сохраните результат.

**Пример:** `ssh-keygen -F ВАШ_СЕРВЕР -f ~/seminar-08/ssh/course-known-hosts` →
`# Host ВАШ_СЕРВЕР found: line 1` и следом строка с ключом.

### M5. Диагностика соединения

**need:** учебный SSH-сервер.

Проверьте соединение без интерактивного терминала. Сохраните максимальную клиентскую диагностику, stdout и код завершения раздельно.

**Пример:** в файле диагностики есть строки `Server host key: ...`,
`Offering public key: ...` и `Authenticated to ...`; код завершения — `0`.

### M6. Цепочка через jump-host

**need:** данные учебного сервера; имя внутреннего хоста (можно вымышленное).

Опишите в своём SSH-config внутренний хост `lab`, доступный только через
`course`, и покажите — не подключаясь, — что клиент пойдёт до него через
bastion. Объясните в комментарии, почему это лучше, чем зайти на `course` и
запустить `ssh lab` уже оттуда.

**Пример:** `ssh -T -F ~/seminar-08/ssh/course-config -G lab` → строки
`hostname 10.0.0.7` и `proxyjump course`.

### M7. Разбор отказа в аутентификации

**need:** учебный SSH-сервер.

Сгенерируйте заведомо посторонний ключ и попробуйте войти с ним, запретив
клиенту предлагать любые другие ключи. Сохраните полный клиентский лог и
выпишите из него строки, по которым видно: до какого шага дошло соединение,
какой ключ был предложен и что сервер готов был принять.

Учтите: `IdentitiesOnly=yes` оставляет ключи из `-i` **и** из `IdentityFile`
вашего конфига, поэтому с псевдонимом `course` клиент подставит правильный ключ
и войдёт. Чтобы отказ действительно произошёл, конфиг надо обойти.

**Пример:** в логе есть `Offering public key: keys/wrong_key`, следом
`Authentications that can continue: publickey`, завершается всё
`Permission denied (publickey)`, код возврата — `255`.

## Сложное — 7 задач

### H1. Доступ по ключу

**need:** учебный SSH-сервер с входом по паролю; пара `~/seminar-08/keys/course_ed25519`; `ssh-copy-id`.

Добавьте публичный ключ в `authorized_keys` сервера. Подключитесь только с выбранным закрытым ключом. Сохраните удалённого пользователя и fingerprint ключа.

**Пример:** `ssh -o IdentitiesOnly=yes -i ... course whoami` → ваш логин на
сервере, пароль при этом не спрашивается.

### H2. Обновление каталога

**need:** учебный SSH-сервер; `rsync`; локальная и удалённая копии каталога.

Измените, добавьте и удалите локальные файлы. Сохраните предварительный план синхронизации с удалением и затем приведите удалённую копию к локальному состоянию.

**Пример:** в плане (`-n`) строки вида `<f.st......` для изменённого файла,
`<f+++++++++` для нового и `*deleting   b.txt` — для удалённого (`<` значит
«поедет на удалённую сторону»).

### H3. Туннель и отказ

**need:** учебный SSH-сервер; удалённый HTTP-сервис с PID в `~/http-server.pid`; `curl`.

Создайте туннель с проверкой успешного проброса. Сохраните успешный HTTP-ответ, затем остановите сервис и сохраните ошибку запроса.

**Пример:** первый `curl http://127.0.0.1:9000` возвращает страницу и код `0`;
после остановки сервиса тот же `curl` завершается ненулевым кодом — обычно `56`
(`Recv failure`), а не `7`: локальный порт по-прежнему открыт самим `ssh`,
соединение принимается и рвётся уже на той стороне.

### H4. Несколько окон tmux

**need:** учебный SSH-сервер с `tmux`.

Создайте detached-сессию `course-lab` с окнами `system` и `worker`. В первом сохраните сведения о системе, во втором — о нагрузке; обе команды должны оставить окно работающим. После повторного подключения сохраните список окон и содержимое обеих панелей, затем завершите сессию.

**Пример:** `tmux list-windows -t course-lab` → две строки, `system` и
`worker`; `capture-pane -p -t course-lab:system` печатает вывод `uname -a`.

### H5. Резервная копия через SSH

**need:** учебный SSH-сервер; `rsync`; каталог `project`.

Создайте удалённую копию `project` без `.git`, `.venv` и `__pycache__`. Сохраните предварительный план и итоговые списки файлов с обеих сторон.

**Пример:** в плане нет ни одной строки с `.git/` или `__pycache__/`, а
удалённый листинг совпадает с локальным по составу файлов.

### H6. Обратный туннель

**need:** учебный SSH-сервер; `python3`; `curl` на сервере.

Поднимите HTTP-сервис на своей машине так, чтобы он слушал только `127.0.0.1`,
и отдайте его на сервер обратным пробросом. Убедитесь **командой, выполненной
на сервере**, что сервис оттуда доступен, и приберите за собой оба процесса.

**Пример:** `ssh course 'curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:20090'`
→ `200`, а после остановки туннеля та же команда завершается ошибкой.

### H7. Журнал попыток входа и `fail2ban`

**need:** своя виртуальная машина с `sudo`; SSH-сервер, доступный из интернета; установленный `fail2ban`.

Выгрузите журнал службы SSH за сутки, посчитайте неудачные попытки входа и
постройте топ адресов, с которых они шли. Покажите состояние `fail2ban` для
jail `sshd` и объясните в комментарии, почему `fail2ban` не заменяет вход по
ключам.

**Пример:** `grep -c 'Failed password'` → число вида `1274`;
`sudo fail2ban-client status sshd` → строки `Currently banned:` и
`Total banned:` с ненулевыми значениями.
