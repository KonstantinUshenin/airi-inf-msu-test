# Практическая работа

**Выход:** лог терминала (`.sh` или текстовый файл с командами и выводом) либо
ссылка на репозиторий. Работаем **в терминале**; графические клиенты и панель
Git в редакторе на этом семинаре не используем.

Все задачи выполняются **на своей виртуальной машине, в домашнем каталоге**
(например, в `~/seminar-04/`). Каталог `/tmp` не используем: он вычищается при
перезагрузке, а репозитории задач должны сохраниться до защиты.

Задачи разбиты на три уровня. Базовые задачи — обязательный минимум, по ним
отмечают, кто их решил. Список задач с запасом — преподаватель выбирает, что
давать.

> Задачам M8, M9 и H7 нужен доступ к серверу (GitHub, GitLab или Gitea) —
> уточните у преподавателя, какой платформой пользуетесь.

## База

### B1. Первый репозиторий

**need:** установленный `git`, терминал.

Создайте каталог проекта и инициализируйте в нём репозиторий; настройте git так,
чтобы основная ветка называлась `main`, и задайте своё имя и почту. Создайте файл
`train.py`, который печатает значение метрики, и сделайте первый коммит с
сообщением по Conventional Commits (`тип(область): что сделать`, без точки в
конце). Покажите историю в кратком виде и выведите для последнего коммита его
полный хэш, короткий хэш, автора и дату.

**Пример:** `git log --oneline` → одна строка вида
`a1b2c3d feat(train): добавить baseline-эксперимент`.

### B2. Три зоны и индекс

**need:** репозиторий из B1; раздел 7 микро-лекции (индекс).

Измените значение метрики в `train.py`. Не делая коммита, покажите
последовательно: состояние репозитория, разницу между рабочей копией и
индексом, ту же разницу после `git add`, и разницу между индексом и последним
коммитом. Объясните в комментарии, почему после `git add` первая разница
опустела. Завершите коммитом.

**Пример:** до `git add` вывод `git diff` непустой, после — пустой, а
`git diff --cached` показывает те же строки `-`/`+`.

### B3. Восстановление после катастрофы

**need:** репозиторий с хотя бы одним коммитом.

Удалите из рабочей копии все файлы с кодом. Покажите, что git заметил пропажу,
и восстановите их одной командой. Затем создайте новый файл, **не** добавляя
его в git, удалите его тем же способом и покажите, что восстановить его уже не
получится. Объясните разницу.

**Пример:** после `rm *.py` строка ` D train.py` в `git status --short`; после
`git restore .` файл снова на месте и `git status` пуст.

### B4. Уборка мусора

**need:** репозиторий из B1.

Создайте в репозитории несколько файлов и каталогов, не находящихся под
контролем версий (имитируйте кэши и чекпойнты). Сначала выведите список того,
что будет удалено, **не удаляя**, затем удалите. Покажите, что отслеживаемые
файлы при этом не пострадали.

**Пример:** `git clean -nd` печатает строки `Would remove ...`; после
`git clean -fd` вывод `git status --short` пуст, а `train.py` на месте.

### B5. `.gitignore`

**need:** репозиторий из B1.

Напишите `.gitignore`, который скрывает: один конкретный файл с секретами,
каталог с данными целиком, все файлы по маске расширения — и при этом делает
исключение для одного файла, попадающего под маску. Создайте соответствующие
файлы и покажите, что git видит только нужные. Для каждого скрытого файла
выведите, какое именно правило сработало. Закоммитьте `.gitignore`.

**Пример:** `git check-ignore -v model.pt` → `.gitignore:8:*.pt	model.pt`.

### B6. Ветка и слияние

**need:** репозиторий из B1.

Создайте ветку под отдельную гипотезу, сделайте в ней коммит, вернитесь на
`main` и влейте ветку обратно. Убедитесь, что слияние прошло без конфликта, и
удалите ветку. Покажите историю с графом ветвлений.

**Пример:** `git branch` после решения содержит только `main`, а
`git log --oneline` включает коммит, сделанный в ветке.

### B7. Читаемая история

**need:** репозиторий с несколькими коммитами и хотя бы одной веткой.

Настройте алиас `lg`, показывающий историю одной строкой на коммит, с графом
ветвлений, подписями веток и по всем веткам сразу. Выведите историю этим
алиасом. Отдельно покажите, какие файлы и как изменил один конкретный коммит,
обратившись к нему по короткому хэшу.

**Пример:** `git lg` → `* a1b2c3d (HEAD -> main) Слить feature/augmentation`;
`git show --stat a1b2c3d` → строка `train.py | 2 +-`.

### B8. Что внутри `.git`

**need:** репозиторий из B1; раздел 13 микро-лекции.

Не пользуясь `git log`, определите по содержимому каталога `.git`, на какой
ветке вы находитесь и на какой коммит она указывает: найдите файл, где записана
текущая ветка, и файл, где лежит хэш её последнего коммита. Убедитесь, что
найденный хэш совпадает с тем, что печатает `git rev-parse HEAD`. Затем создайте
новую ветку и покажите, что появилось на диске.

**Пример:** `cat .git/HEAD` → `ref: refs/heads/main`;
`cat .git/refs/heads/main` → тот же хэш, что и у `git rev-parse HEAD`.

### B9. Соглашения об именах

**need:** репозиторий из B1.

Создайте ветку с небрежным именем (`мои-правки`) и переименуйте её по
соглашению `<тип>/<описание>`. Сделайте в ней коммит, сообщение которого
состоит из заголовка и тела, разделённых пустой строкой; покажите, что
`git log --oneline` печатает только заголовок, а полный вид — весь текст.

Затем сделайте коммит с намеренно плохим сообщением (`правки`) и исправьте
сообщение, **не создавая** нового коммита. Покажите хэш до и после исправления и
объясните в комментарии, почему так нельзя делать с коммитом, который уже
выложен на сервер.

**Пример:** `git branch -m мои-правки feature/augmentation`; после
`git commit --amend` заголовок в `git log --oneline` изменился, и хэш коммита
тоже стал другим.

## Среднее

### M1. Конфликт слияния

**need:** репозиторий из B1.

Организуйте конфликт: измените **одну и ту же строку** файла по-разному на двух
ветках и слейте их. Покажите код возврата `git merge` и содержимое файла с
маркерами конфликта. Разрешите конфликт вручную, оставив осмысленный вариант, и
завершите слияние. Покажите итоговый граф.

**Пример:** после `git merge` файл содержит строки `<<<<<<< HEAD`, `=======`,
`>>>>>>>`; после разрешения `git status` чист, а `git log --graph` показывает
ромб слияния.

### M2. Файл в состоянии другой ветки

**need:** две ветки, в которых один файл различается.

Находясь на `main`, приведите **один** файл к тому состоянию, в котором он
находится на другой ветке, не переключаясь на неё. Покажите, что текущая ветка
не изменилась, а репозиторий стал грязным. Откатите изменение. Затем повторите
то же самое, взяв файл не из ветки, а из коммита двухшаговой давности.

**Пример:** `git restore --source=experiment/lr -- train.py`, после чего
`git branch --show-current` по-прежнему печатает `main`, а `git status --short`
показывает ` M train.py`.

### M3. `revert` против `reset`

**need:** репозиторий с тремя-четырьмя коммитами.

Отмените последний коммит двумя разными способами. Сначала — сдвинув ветку
назад так, чтобы коммит исчез из истории, и восстановите состояние обратно.
Затем — создав новый коммит, отменяющий изменения предыдущего. Покажите историю
после каждого способа и объясните в комментарии, какой из них допустим для
ветки, уже выложенной на сервер, и почему.

**Пример:** после `git reset --hard HEAD~1` в `git log --oneline` на одну
строку меньше; после `git revert` — на одну строку **больше**, а содержимое
файлов совпадает с состоянием до отменённого коммита.

### M4. Отложить работу

**need:** репозиторий с незакоммиченными изменениями; раздел 8 микро-лекции
(`git stash`).

Начните правку файла, не доводя её до коммита. Выяснилось, что срочно нужно
переключиться на другую ветку. Отложите незавершённую работу так, чтобы
репозиторий стал чистым, переключитесь, вернитесь обратно и восстановите
отложенное. Покажите список отложенных изменений на промежуточном шаге.

**Пример:** после `git stash` вывод `git status` пуст, `git stash list`
содержит одну запись; после `git stash pop` правка снова в рабочей копии.

### M5. Перенос коммита

**need:** ветка с несколькими коммитами; раздел 9 микро-лекции (`cherry-pick`).

В ветке сделано три коммита, но в `main` нужен только один из них — например,
исправление опечатки. Перенесите в `main` **только** этот коммит, не сливая
ветку целиком. Покажите, что в `main` появились изменения только из него, а
хэши исходного и перенесённого коммитов различаются.

Переносите коммит, который правит файл, **существовавший до ветвления**: коммит,
опирающийся на соседние коммиты той же ветки, накладывать будет не на что, и вы
получите конфликт вместо переноса.

**Пример:** `git cherry-pick <хэш>` → в `git log --oneline` ветки `main`
появляется коммит с тем же сообщением, но другим хэшем.

### M6. Кто изменил эту строку

**need:** файл с историей из нескольких коммитов от разных авторов (или с
разными сообщениями); раздел 12 микро-лекции (`git blame`).

Для заданного файла выясните, каким коммитом, когда и кем в последний раз
изменена конкретная строка. Ограничьте вывод диапазоном строк. Затем найдите
все коммиты, в которых в проекте появлялась или исчезала строка с определённой
подстрокой (например, имя гиперпараметра).

**Пример:** `git blame -L 1,1 train.py` → `a1b2c3d (Student 2026-09-01 1) accuracy = 0.71`.

### M7. Лишний файл в репозитории

**need:** репозиторий, в котором закоммичен файл-чекпойнт.

Файл с весами модели по ошибке попал в коммит. Добавьте его под соответствующее
правило в `.gitignore` и покажите, что этого **недостаточно** — git продолжает
его отслеживать. Уберите файл из-под контроля версий, не удаляя его с диска, и
покажите, что теперь правило работает.

**Пример:** после `git rm --cached model.pt` и коммита вывод `git status --short`
пуст, при этом `ls model.pt` файл находит.

### M8. Работа с upstream

**need:** аккаунт на платформе курса; учебный репозиторий, указанный
преподавателем.

Сделайте форк учебного репозитория и склонируйте свой форк. Добавьте
оригинальный репозиторий вторым удалённым под именем `upstream` и покажите
список удалённых репозиториев. Скачайте изменения из `upstream`, влейте их в
свою основную ветку. Создайте ветку под задачу, сделайте коммит, выложите ветку
в свой форк и откройте pull request.

**Пример:** `git remote -v` показывает две записи — `origin` (ваш форк) и
`upstream` (оригинал), каждая в двух строках `(fetch)` и `(push)`.

### M9. Настройка доступа

**need:** аккаунт на платформе курса.

Настройте доступ к своему репозиторию **одним** из двух способов и проверьте
его рабочим `git push`:

- по HTTPS с персональным токеном (PAT) — с ограниченным сроком жизни и
  минимально необходимыми правами, с сохранением через `credential.helper`;
- либо по SSH — сгенерировав ключ `ed25519` и добавив открытую часть в
  настройки аккаунта.

Покажите вывод проверочной команды. В комментарии объясните, почему **нельзя**
вписывать токен прямо в адрес удалённого репозитория.

**Пример:** `ssh -T git@github.com` → `Hi <username>! You've successfully
authenticated, but GitHub does not provide shell access.`

### M10. Реверс-инженерия объектов

**need:** репозиторий из B1; `python3`; раздел 13 микро-лекции.

Разберите последний коммит по цепочке `commit → tree → blob`, пользуясь только
`git cat-file`: покажите тип объекта коммита, его содержимое, содержимое
`tree`, на который он ссылается, и содержимое `blob` файла `train.py`. Ответьте
в комментарии, в каком из трёх объектов хранится **имя** файла.

Затем добавьте в базу объект вручную командой `git hash-object -w` (без `add` и
без коммита), найдите созданный файл в `.git/objects` и распакуйте его на
питоне через `zlib`, показав заголовок и содержимое. Проверьте, что повторный
`git hash-object` того же содержимого даёт тот же хэш, а изменение одного
символа меняет его целиком.

**Пример:** `git cat-file -t HEAD` → `commit`; распаковка объекта даёт
`blob 13\0привет`.

## Сложное

### H1. Поиск сломавшего коммита

**need:** репозиторий, в котором есть скрипт, печатающий метрику, и не менее
десяти коммитов; в одном из них метрика падает; раздел 12 микро-лекции
(`git bisect`).

Известно, что десять коммитов назад метрика была в порядке, а сейчас упала.
Найдите первый коммит, в котором она испортилась, **бинарным поиском** —
сначала вручную, отмечая проверенные состояния как хорошие и плохие, затем
автоматически, написав скрипт-проверку, который возвращает нулевой код для
хорошего состояния. Сравните число шагов с перебором подряд.

**Пример:** `git bisect run ./check.sh` завершается строкой
`<хэш> is the first bad commit` примерно за 4 шага вместо 10.

### H2. Восстановление потерянного

**need:** репозиторий с несколькими коммитами.

Устройте две потери и восстановите обе. Первая: сдвиньте ветку на несколько
коммитов назад так, что последние коммиты пропадут из истории, — верните их.
Вторая: удалите ветку, не слитую в `main`, — восстановите её вместе с
коммитами. В обоих случаях найдите нужную точку по журналу перемещений `HEAD`.

**Пример:** `git reflog` содержит строку `HEAD@{1}: commit: ...`, после
`git reset --hard HEAD@{1}` история восстановлена.

### H3. Секрет в истории

**need:** тестовый репозиторий, который не жалко; желательно `git-filter-repo`.

Закоммитьте файл с «токеном», сделайте после этого ещё пару коммитов, а затем
удалите файл обычным коммитом. Покажите, что содержимое токена **по-прежнему**
достаётся из истории. После этого вычистите файл из всех коммитов целиком и
покажите, что он больше не находится. В комментарии перечислите, что нужно
сделать в реальной ситуации помимо чистки истории.

**Пример:** после `git rm` и коммита команда `git log -p -- secrets.env`
всё ещё печатает содержимое токена; после чистки истории
`git log --all --oneline -- secrets.env` не выводит ничего.

### H4. Версионирование большого файла

**need:** установленный `git-lfs`.

Настройте в репозитории хранение файлов по маске через Git LFS. Закоммитьте
крупный бинарный файл (сгенерируйте его), измените и закоммитьте второй раз.
Покажите, что в самом репозитории вместо файла лежит текстовый указатель, и
выведите список файлов, которые ведутся через LFS.

**Пример:** `git show HEAD:model.pt | head -3` печатает строки
`version https://git-lfs.github.com/spec/v1` и `oid sha256:...` вместо двоичных
данных.

### H5. Защита от собственной ошибки

**need:** репозиторий из B1; раздел 19 микро-лекции (хуки).

Напишите хук `pre-commit`, который не даёт создать коммит, если в него попал
файл по запрещённой маске или файл размером больше заданного порога. Хук должен
печатать понятное сообщение и завершаться ненулевым кодом. Проверьте, что
обычный коммит проходит, а запрещённый — отклоняется. В комментарии укажите,
почему на хуки нельзя полагаться как на единственную защиту.

**Пример:** `git commit -m "test"` с добавленным `model.pt` печатает
`Отклонено: model.pt (12 МБ) — используйте Git LFS` и коммит не создаётся.

### H6. Конфликт в ноутбуке

**need:** `jq` или `nbdime`; репозиторий с `.ipynb`; раздел 17 микро-лекции.

Устройте конфликт в файле `.ipynb`, изменив одну и ту же ячейку на двух ветках.
Покажите, почему обычное разрешение конфликта здесь неудобно. Разрешите его
осмысленно — с помощью инструмента, понимающего структуру ноутбука, либо
приведя файл к виду, пригодному для сравнения. Предложите правило работы с
ноутбуками в git, снижающее вероятность таких конфликтов.

**Пример:** `git diff` на `.ipynb` показывает конфликт внутри JSON вперемешку с
`execution_count` и выводами ячеек; `nbdiff` показывает только изменившийся
текст ячейки.

### H7. Конфликт в паре

**need:** работа вдвоём, общий репозиторий на сервере, у обоих есть доступ на
запись (задача M9).

Оба участника клонируют один репозиторий и, не сговариваясь, правят **одну и
ту же строку** одного файла, коммитят и пытаются выложить изменения. Первый
выкладывает успешно, второй получает отказ. Второй участник должен скачать
чужие изменения, разрешить конфликт и выложить результат так, чтобы **обе**
правки остались в истории. Приложите итоговый граф истории и объясните, что
означал текст отказа.

**Пример:** `git push` у второго участника завершается ошибкой
`! [rejected] main -> main (fetch first)`; после `git pull` и разрешения
конфликта `git log --graph` содержит коммит слияния с двумя родителями.

### H8. Распухший репозиторий

**need:** репозиторий, который не жалко (можно каталог демонстрации из
микро-лекции); желательно `git-filter-repo`.

Измерьте размер `.git`. Закоммитьте файл на 20 МБ случайных данных (`head -c
20000000 /dev/urandom > checkpoint.pt`), измерьте снова. Удалите файл обычным
коммитом и покажите, что размер `.git` **не уменьшился**; объясните в
комментарии, почему. Попробуйте `git gc` и посмотрите, помогает ли упаковка на
случайных данных.

После этого вычистите файл из всех коммитов истории (механика та же, что в H3),
просрочьте reflog и запустите сборку мусора так, чтобы `.git` действительно
уменьшился до исходного размера. Приведите замеры до/после и ответьте, что
произойдёт с коллегой, который склонировал репозиторий до чистки.

**Пример:** `du -sh .git` → `404K` → `20M` → после `git rm` и коммита всё ещё
`20M` → после чистки истории и `git gc --prune=now` снова около `404K`;
`git count-objects -vH` показывает, что объекта больше нет.

### H9. Проверка соглашений автоматикой

**need:** репозиторий из B1; второй репозиторий, созданный через `git init
--bare`, в роли сервера (что это такое — раздел 14); раздел 19 микро-лекции
(хуки).

Соглашение, которое никто не проверяет, соблюдается примерно наполовину.
Настройте репозиторий так, чтобы нарушения отбивались сами:

1. хук `commit-msg` — отклоняет коммит, если заголовок не подходит под
   Conventional Commits (`тип(область): описание`) или длиннее 72 символов;
2. хук `pre-push` — отклоняет отправку ветки, имя которой не соответствует
   `<тип>/<описание>` (ветку `main` пропускает);
3. храните хуки **не** в `.git/hooks`, а в каталоге внутри репозитория, и
   подключите их через `core.hooksPath`. Объясните в комментарии, зачем так.

Покажите, что плохой коммит и push ветки с плохим именем отбиваются, а
исправленные проходят. Затем обойдите собственный хук одним флагом `git commit`
и объясните, почему локальные хуки — это удобство, а не гарантия, и что нужно
настроить на стороне сервера, чтобы запушить нарушение было **нельзя**.

**Пример:** `git commit -m "правки"` завершается с кодом 1 и сообщением хука;
`git push origin мои-правки` — отказом `pre-push: имя ветки ... не по
соглашению`; `git commit -m "правки" --no-verify` проходит.

### H10. Pull request с ревью и автопроверкой

**need:** работа вдвоём; общий репозиторий на сервере, у обоих есть доступ на
запись (задача M9); разделы 20 и 21 микро-лекции.

Пройдите полный командный цикл на маленькой задаче — например, «добавить в
`train.py` функцию, считающую среднее по списку, и тест к ней».

Участник A: заводит ветку по соглашению, делает изменение, добавляет в
репозиторий пайплайн (`.gitlab-ci.yml` или `.github/workflows/ci.yml`), который
на каждый push запускает тесты, и открывает pull request. Покажите, что
пайплайн отработал, и что он **краснеет**, если тест сломать.

Участник B: делает ревью — оставляет минимум два предметных замечания к коду в
самом pull request'е (не в мессенджере).

Участник A: отвечает на замечания и правит их **новыми коммитами** в ту же
ветку. Покажите, что pull request обновился сам и пайплайн прогнался заново.

Влейте pull request, когда проверки зелёные и ревью одобрено, и удалите ветку.
В комментарии ответьте: что из ваших замечаний мог бы найти линтер, а что —
только человек.

**Пример:** в pull request видно несколько итераций коммитов, красный и затем зелёный
статус пайплайна и тред с обсуждением; после мёрджа `git log --graph` в `main`
содержит коммит слияния.
